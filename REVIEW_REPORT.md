## Findings and changes

| Area | Root cause and disposition |
|---|---|
| Opening entry | Original `frontend/dashboard/inventory.html:76` only offered pieces, packs and bags, multiplied in browser floating-point, and described all base units as pieces. This could give incorrect balances and did not retain entered-unit evidence. Patch sends a unit and optional explicit factor; server converts using Decimal, records entered quantity/unit/factor in movement metadata, keeps base unit, and uses a stable modal key. Container factors are entered for that item/operation, never inferred from its generic saved pack size. Opening cost is per base unit. Metric conversions use the existing converter; shot conversions require an explicit factor. |
| Duplicate openings | Original opening endpoint generated a fresh UI key per submit and accepted new keys for the same item/location. Patch serializes on the item row and blocks a second opening for that pair, while returning the original movement for a valid same-key retry. This policy affects the API endpoint; other direct service callers still have their original source-key semantics. Existing historical openings are not modified. For corrections use an approved count/adjustment, not a second opening. A retry with a changed key is rejected, not silently treated as success. |
| Add item | Original `backend/apps/inventory/views.py:107–120` created an item before optional opening entry and silently skipped nonexistent/inactive locations; frontend did not send opening fields or refresh the catalog. Patch validates optional opening fields, stores the item and opening movement atomically, and refreshes both tables. Modal infrastructure already guards in-flight submission; duplicate SKU remains a database/serializer guard. A lost create response followed by a retry may return a duplicate-SKU error rather than replaying the original item; staff should search the catalog before retrying. |
| Prices | `StockItem.standard_cost` is a reference purchase cost per base unit; `pack_price` is an actual pack-price reference and can derive standard cost, while goods receipt and movement costs preserve transaction evidence. Menu `base_price` is the selling price. These are not interchangeable; no field or column was deleted. Opening UI now labels cost as per base unit. Receipt-based valuation and prior movement costs are unchanged. The add/edit UI still has pack and standard-cost inputs; resolving their conflicting precedence requires a broader purchasing/valuation review. |
| Stock state | Original `needs_reorder` already used `quantity_on_hand <= reorder_level`, but combined zero and low into a single label. Patch adds server-generated `stock_state` with out (<=0), low (>0 and <= threshold), or adequate (>threshold); table uses text and different border patterns. Existing reorder filter and profitability `needs_reorder` retain their original <= rule, so out-of-stock is included in the reorder filter. There is **no new low-stock notification**, and dashboard-wide state/notification consistency is not established. Missing balance rows are not synthesized as out of stock. |
| Ledger filters | Server already accepted exact `type`, item, location, department and date filters. Original ledger selector omitted `TRANSFER_OUT`, `TRANSFER_IN`, `POS_RETURN`, and `MAINTENANCE_RETURN`; patch adds the actual values without changing the backend filtering contract. Two separate transfer directions are offered, not an invented aggregate type. |
| Menu category | Original `frontend/dashboard/pos.html:903–905` uses operational `state.menu`, which is mode-filtered; the management category endpoint already scopes results to permitted service areas. Separate `dependency_patches/pos_menu_categories.patch` fetches all active categories available to that user's menu-management permissions and labels the service area. It does not change the ordering screen. Review it separately; backend validation for a category deactivated between selection and save remains unresolved, and no browser end-to-end test was performed. |
| Recipes | Existing `StockRecipe`/`StockRecipeLine` store versioned multiple ingredients and per-menu-unit quantities; snapshotting preserves old consumption. Existing `pos_stock_summaries` uses the scarcest component, and order submission and delivery use existing validation and inventory hand-off. New regression covers a two-ingredient scarcest case. UI can create a new version, but does not prefill an edit from the existing recipe; it uses a free-text unit rather than a compatible-unit picker. No batch-yield field was found in these models; no yield or example recipe was invented. The recipe modal still generates its key inside the submit callback, so a lost response/retry can create another version. No changes were made to recipe logic. |
| Conversion risk, **unresolved** | Existing `inventory_service.py:734–740` applies one `units_per_pack` value to *any* container type for recipe conversion, and `:673` assumes a 50 ml shot. An item can have differently sized containers, so this is not an adequate item-and-package-specific conversion model. The opening patch deliberately does not reuse the container fallback and does not assume shot size, but existing recipe and other users of the converter remain exposed. Do not configure a container recipe until a separately reviewed conversion model and data migration are implemented. Existing recipes require an operator audit; do not retroactively change ledger history. |
| Inventory cleanup | Base-unit form choices lacked gallons, buckets and sachets; these were added. Existing `StockItemSerializer` can still change a base unit on an item with historical balances/movements; preventing or migrating such changes needs a compatibility/data audit before deployment. Catalog pack labels still assume pieces; no schema cleanup was attempted. |

## Model, fields and migration changes

No database model, field, column or migration was changed or removed. Additive API-only changes: `OpeningStockSerializer` accepts `unit` and `conversion_factor`, and balance output adds `stock_state`. Opening evidence uses the existing `StockMovement.metadata` JSON field. The new one-opening-per-item/location endpoint policy may reject previously accepted repeat openings; review existing workflows and records before rollout. Item create now rejects incomplete/invalid optional opening input rather than silently ignoring it. There is no backfill or automatic historical revaluation.

The existing `StockItem` package fields, `StockBalance`, immutable `StockMovement`, receipts, accounting records, `StockRecipe` versioning, and POS menu prices are retained. Rollback of code does not reverse stock already posted while the patch was active; restore code only after reconciling and backing up ledger/balance data, and use approved compensating entries if corrections are needed.

## Remaining dependencies and verification gaps

- **Notifications:** no trigger/policy, deduplication, restoration handling or permission-targeted low-stock notifications were implemented; the existing notification service must be integrated with stock transitions, not page refreshes. Dashboard-wide summaries remain unaudited for exact state consistency.
- **Persistent conversion configuration:** schema lacks a package-unit identifier attached to `units_per_pack`; recipe conversions can conflate carton/crate/bag. A safe design needs explicit item+from-unit+to-unit factors, data reconciliation, permission checks, audit, staged backfill, rollback and concurrency tests. Procurement receipts have their own pack/piece UI and must be reviewed separately. Existing `50 ml` shot assumption needs hotel confirmation.
- **POS / Room Service:** existing order service checks stock at submission and consumes on delivery, not at initial order submission; verify this lifecycle with hotel operations. The code retains durable hand-offs and can park unresolved shortages; do not assume all delivery failures roll back without checking the exact recovery policy. Restaurant and room-service UI were not manually exercised. The separate POS category patch needs browser, RBAC, stale/inactive-category and API integration tests before adoption.
- **Recipes:** no prefilling edit workflow, unit picker, batch-yield support or dedicated concurrent recipe/order tests were added. Existing no-recipe/NO_STOCK policy allows untracked items rather than claiming all dishes are available; hotel must decide which prepared items must be blocked until configured.
- **Accounting and Procurement:** no implementation files changed. Opening-cost and pack-price behavior should be reconciled with actual hotel accounting practices. A generic current cost is not a substitute for historical receipt valuation.
- **Integrity:** one-opening-per-location policy is enforced by this endpoint and its item-row lock, not by a new database constraint or all direct service calls. Existing old/different writers or a mixed-version deployment can bypass it. Test concurrency on the actual database engine, including mixed writers and uniqueness errors. Running copies of old frontend and new backend together changes the old pack-conversion behavior; deploy both after testing and clear caches.
- **Validation and usability:** no browser-based field-error mapping, screen-reader audit, confirmation dialog for opening stock, maximum accumulated balance overflow test, or retry-after-network-loss integration test was completed. Existing forms have other historical hardcoded piece/currency assumptions.
