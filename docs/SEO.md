# SEO, indexing and local search — implementation and maintenance

This document describes the SEO layer added to the J-ONE Hotel & Lodge website:
what it does, why each decision was made, and how to change it safely.
Owner-facing Google setup (Search Console, Business Profile) is in
[GOOGLE_SETUP.md](GOOGLE_SETUP.md).

---

## 1. The one rule: there is a single source of truth

Every SEO signal for every public page lives in **`frontend/seo_build.py`**:

| What | Where |
|---|---|
| Title, meta description, canonical URL, robots directive | `PAGES` dict — one entry per page |
| Open Graph / Twitter card | generated from `PAGES` + `SITE` |
| JSON-LD (Hotel, WebSite, WebPage, BreadcrumbList) | `hotel_node`, `website_node`, `webpage_node`, `breadcrumb_node` |
| `sitemap.xml` | `sitemap_xml()` — built from `PAGES` |
| `robots.txt` | `robots_txt()` — built from `ROBOTS_DISALLOW` |
| Verified business facts (name, phone, email, address, amenities) | `SITE` |

`frontend/build.py` calls this layer on every build, so the page head, the
sitemap and robots.txt can never disagree with each other. The generated tags
sit between these markers in each page:

```html
<!-- SEO:BEGIN — generated by frontend/seo_build.py; edit PAGES there, not here -->
...
<!-- SEO:END -->
```

Hand-edited copies of `<title>`, `<meta name="description">`, `og:*`,
`twitter:*`, `rel="canonical"`, `<meta name="robots">` or JSON-LD outside those
markers are **removed on the next build**. To change a title, change `PAGES`.

### Commands

```bash
cd frontend
python3 build.py                 # rebuild chrome + SEO + sitemap + robots, then VALIDATE
python3 build.py --bump patch    # release: bumps version.json, sw.js cache, asset stamps
python3 seo_build.py --check     # validate the built files only (no writes)
python3 validate.py              # existing HTML/JS validator
node --test tests-js/test-seo.js # 21 SEO contract tests
```

A build **fails** if SEO validation fails — a duplicate title, an empty
description, a canonical off the canonical origin, a noindex page in the
sitemap, a missing Open Graph image or fabricated rating markup can never be
released.

## 2. Canonical origin and URL shape

* Canonical origin: **`https://jonehotels.com`** (no `www`, HTTPS).
* Cloudflare serves **extensionless** URLs: `/rooms` returns 200, while
  `/rooms.html` returns **307 → `/rooms`**. Canonicals and sitemap entries are
  therefore extensionless. Pointing them at `.html` would point every canonical
  and every sitemap entry at a redirect.
* `www.jonehotels.com` returns 200 today and is **not** 301-redirected to the
  apex. Every canonical is on the apex, so Google consolidates on the apex
  regardless, but a 301 `www → apex` redirect is still recommended (see
  GOOGLE_SETUP.md §5).
* Query parameters used by booking and payment flows are untouched by any
  redirect or canonical rule.

## 3. Indexability map

| Page | Indexed | In sitemap | Notes |
|---|---|---|---|
| `/` (homepage) | yes | yes | Hotel + WebSite + WebPage JSON-LD |
| `/rooms` | yes | yes | crawlable room-type summary added to the initial HTML |
| `/facilities` | yes | yes | crawlable in-room amenities summary |
| `/gallery` | yes | yes | |
| `/offers` | yes | yes | only live offers are rendered by the backend |
| `/about` | yes | yes | |
| `/contact` | yes | yes | Hotel JSON-LD + map + NAP |
| `/policies`, `/privacy`, `/terms`, `/cancellation-policy`, `/refund-policy` | yes | yes | |
| `/review` | yes | **no** | public feedback page, not a search landing page |
| `/booking` | noindex | no | transactional booking flow |
| `/booking-review`, `/booking-confirmation`, `/payment-verify`, `/cancellation-result` | noindex | no | booking-specific, may contain personal data |
| `/my-bookings`, `/login`, `/register`, `/room-details` | noindex | no | account/stateful |
| `/qr-service` | noindex | no | the URL carries a guest bearer token |
| `/dashboard/*`, `/portal/*` | noindex + `robots.txt` + `X-Robots-Tag` | no | authenticated |
| `403`, `404`, `500` | noindex | no | error pages |

`robots.txt` is **not** treated as a security control. Every private route above
is protected by server-side authentication/authorisation; the indexing
directives and `X-Robots-Tag` headers (in `frontend/_headers`) are a second,
independent layer.

## 4. Structured data

Published, all generated from `SITE`:

* **Hotel** (`https://jonehotels.com/#hotel`) on the homepage and contact page:
  name, `alternateName` (`J-ONE Hotel and Lodge`, `J One Hotel`, `Jone Hotels`),
  url, telephone, email, image[], logo, `PostalAddress` (Enugu / Enugu State /
  NG), `currenciesAccepted` NGN, `hasMap` (a Maps **search** for the verified
  address), `amenityFeature[]` (the six amenities the live room catalogue
  confirms), `areaServed` Enugu.
* **WebSite** and **WebPage** on every managed page; **BreadcrumbList** on every
  non-home page.

Deliberately **not** published, because they are not verified:

| Field | Why it is absent |
|---|---|
| `aggregateRating`, `review` | The hotel has no verified public rating on this site. Inventing one is against Google's structured-data policy and would be dishonest. |
| `geo` (latitude/longitude) | No verified coordinates exist in the repository or the public API, and a wrong pin is worse than none. **Action for the owner:** read the exact coordinates from the verified Business Profile and they can be added to `SITE` and `hotel_node()`. |
| `checkinTime` / `checkoutTime` | The hotel settings payload currently reports 12:00 for both, while the contact page states "Check-in from 2:00 PM". **Action for the owner:** confirm the real times, then they can be published. |
| `priceRange`, `openingHours`, `sameAs` | Not verified / no confirmed profiles. Add `sameAs` only for social profiles the hotel actually owns. |

**Validation:** `python3 seo_build.py --check` and `node --test tests-js/test-seo.js`
verify the JSON parses, the `@context`/`@type` are correct, required properties
are present, breadcrumbs point at canonical URLs, every referenced image exists
on disk, and no rating/review/price/geo node has crept in. Local validation is
structural, not Google's own parser: after deploying, paste
<https://jonehotels.com/> into the
[Rich Results Test](https://search.google.com/test/rich-results) and the
[Schema Markup Validator](https://validator.schema.org/) for Google's verdict.

## 5. Images and Core Web Vitals

| Change | Evidence |
|---|---|
| Homepage hero re-encoded in place (same filenames, same URLs) | 10 images: 1,819 KB → 1,629 KB (−10.4 %); PSNR 38–52 dB per image (mean pixel delta 0.06–2.14 of 255) — visually indistinguishable, above the usual 35 dB threshold |
| `srcset`/`sizes` on the LCP image + matching `<link rel="preload" imagesrcset>` | phones fetch `hero-1-800.jpg` (77 KB) instead of 229 KB |
| Explicit `width`/`height` on every content photograph + the header logo | images without intrinsic dimensions: 9/10 → 0/10 on the homepage |
| `decoding="async"` on below-the-fold images | off main-thread decode |
| `loading="lazy"` preserved below the fold, never on the LCP image | LCP image is `fetchpriority="high"` |

`optimize_images.py` re-runs the JPEG re-encode. It only rewrites a file when it
gains ≥8 %, and never renames, moves or resizes anything — so no HTML, CSS,
service-worker entry or admin-configured image override can break.

**Not done, on purpose:** WebP/AVIF with `<picture>`. `js/site-images.js` swaps
these same `<img>` elements to administrator-uploaded URLs at runtime; a
`<picture>`/`<source>` pair would keep showing the built-in asset and silently
hide a configured hotel photograph. The safe route to modern formats here is an
edge conversion (Cloudflare → Speed → Optimization → Polish, "Convert to WebP"),
or a separate, tested change that also teaches `site-images.js` about `<source>`.

**Measured lab data** (headless Chromium, 5 runs, mobile viewport 412×915,
API requests blocked so the frontend is isolated, local static server):

| Page | Metric | Before | After |
|---|---|---|---|
| `/` | transferred bytes | 1,900.7 KB | **1,732.0 KB** (−8.9 %) |
| `/` | LCP element | `hero-1.jpg` 229 KB, no preload | `hero-1-1200.jpg` 156 KB, preloaded + srcset |
| `/` | images without dimensions | 9 / 10 | **0 / 10** |
| `/` | CLS | 0.00 | 0.00 |
| `/facilities` | CLS | 0.10 | **0.00** |
| `/facilities` | transferred bytes | 740.6 KB | 728.0 KB |
| `/rooms` | transferred bytes | 548.3 KB | 554.5 KB (+1.1 % — the new crawlable room summary) |
| all | JSON-LD blocks | 0 | 1 |

LCP timings on a loopback server are dominated by container noise (before/after
medians 148 ms vs 144 ms); the deterministic wins are the bytes, the preload,
the srcset and the dimension coverage. Real-world LCP must be confirmed from
field data in Search Console Core Web Vitals after deployment.

**Known opportunity not taken:** the homepage ships **six** full-viewport hero
photographs. Because each absolutely-positioned slide is inside the viewport,
`loading="lazy"` does not defer them, so ~1 MB of hero imagery is fetched during
initial load. Trimming the slideshow to three slides (or giving slides 2–6 the
same `srcset` treatment) is the single biggest remaining byte win — but it is a
visible design change, so it is left to the owner.

## 6. Performance and caching cautions

* `robots.txt` and `sitemap.xml` are now served with explicit content types and
  `Cache-Control: public, max-age=3600` in `frontend/_headers`, so a newly
  generated sitemap is not cached for a day or more.
* `sw.js` only ever controls `/dashboard/` (the staff PWA). Public pages register
  no service worker, so a stale cache cannot hide an SEO change or break the
  booking flow.
* No private API response is cached anywhere: the service worker is network-only
  for `/api/`, `/media/`, `/dashboard/`, `/portal/` and `/qr-service.html`.

## 7. Changing things later

| Task | Do this |
|---|---|
| Change a title/description | edit `PAGES` in `seo_build.py`, run `python3 build.py` |
| Add a public page | add it to `PAGES`, add it to `PUBLIC_PAGES`/`EXPECTED_MANAGED` in `build.py`/`tests-js/test-seo.js`, run the build |
| Retire a page | remove it from `PAGES`; the build then drops it from the sitemap automatically |
| Correct the phone number | update `SITE["phone"]` **and** the verified Business Profile **and** the backend `phone` setting — all three must match |
| Add verified coordinates / social profiles | add to `SITE` and `hotel_node()`, then re-run the tests |
| Add an offer that should rank | offers come from the backend; `/offers` is already indexed. Do not create per-offer pages |

Never add: hidden text, keyword-stuffed footers, doorway pages per room type,
invented reviews or ratings, or a second business listing.

### Brand variations and AI discovery

The central Hotel JSON-LD uses alternateName for common J-ONE/J1/J One
spellings and points to the same canonical hotel entity. The optional public
`/llms.txt` gives a short description and links to canonical public pages; it
is a convention, not a search-engine standard or an indexing guarantee. Keep
its facts aligned with the verified SITE record. Private areas still require
server-side authorization: robots rules are not a security boundary. External
crawling, indexing, brand association and AI recommendations depend on each
platform; no ranking or recognition is guaranteed. Verify ownership and submit
the sitemap to search engines separately, and monitor their indexing reports.
